# デプロイ（担当C / C-8）

**採用：部活の仮想サーバー。** 2026-10 以降，実際にここで稼働している。

当初は無料枠の外部ホスティングを前提に比較していたが，部活の仮想サーバーを使える
ことになったのでそちらにした。SQLiteをそのまま置けて，無料枠の制限（スリープ，
クレジット上限）も受けない。

サーバーを運用しているのは**部活の管理者3人**で，3人は同じアカウントを共有している。
**開発チームの3人（README の「製作者」）はサーバーにログインできない**ので，
設定変更・再起動・バックアップはいずれも管理者に依頼することになる。
以下で「3人」と書いてあるのは，断りがなければ**管理者3人**を指す。

**URLを知っていれば誰でも到達できる状態**なので，実在の学籍番号・氏名は
入れない（架空データのみ）。

## サーバーについて分かっていること・いないこと

実地テスト（2026-11-12）を終えた時点の状態。どれも「動くか」ではなく
「**壊れたときに戻せるか**」に効く項目である。

| 項目 | 状態 |
|---|---|
| HTTPS と証明書 | **確認済み．**実機のスマートフォンでログインが保持された（`Secure` 属性を付けているので，HTTPなら保存されずに全リクエストが401になる） |
| DBのバックアップ | **確認済み．**実地テストの直前と直後に管理者が取得した。**定期的に取られているかは未確認** |
| リバースプロキシの段数（`TRUSTED_PROXY_COUNT`） | **確認済み．**実地テストで学内からの登録が通り，同時に学外からの登録が拒否された。この2つが同時に成立するのは設定値が実構成と一致しているときだけである（下記） |
| `DATABASE_URL` の実際のパス | **あえて記録しない**（下記） |

### DBのパスをこの文書に書かない理由

運用側は把握しており，**復元を実行するのもサーバーに入れる人**である。
開発チームはログインできないので，値を知っていても使い道がない。
一方でこの文書は公開するため，サーバー内のパスを書けば攻撃側の足がかりになる
（こちらには利益が無い）。`CAMPUS_IP_RANGES` をリポジトリに書かないのと同じ理由である。

復元の手順は「`DATABASE_URL` が指す場所にコピーする」という形にしてあり，
**具体的なパスを必要としない**（「バックアップと復元」を参照）。

## 検討した外部ホスティング（不採用）

採用しなかったが，比較は判断の理由として残す。2026-08-22時点の公式情報で，
HTTPS、秘密値の管理、SQLiteの永続化を必須条件としていた。

| 候補 | HTTPS | 環境変数・秘密値 | SQLiteの永続化 | 無料利用 | 判断 |
|---|---|---|---|---|---|
| Render | 自動TLS、HTTPはHTTPSへリダイレクト | DashboardのEnvironmentで設定 | Free Web Serviceは永続ディスク不可 | 750時間/月。ただし15分無通信で停止し、再起動に約1分 | SQLiteのままでは不可。Postgres移行か有料ディスクが必要 |
| Railway | 自動SSL、提供ドメインあり | ServiceのVariablesで設定 | FreeでもVolume上限0.5GB | 月$1相当の無料クレジット | 小規模な実機試験の第一候補 |
| Fly.io | 証明書とVolumeを提供 | `fly secrets` で設定 | Volumeは$0.15/GB/月 | 常設の無条件無料枠ではなく従量課金 | 制御性は高いが今回の「無料枠」優先には不向き |

公式資料：
- Render: https://render.com/docs/web-services
- Render Free: https://render.com/docs/free
- Railway: https://docs.railway.com/pricing/plans
- Railway Networking: https://docs.railway.com/networking/public-networking
- Railway Variables: https://docs.railway.com/variables
- Fly.io: https://fly.io/docs/about/pricing/
- Fly.io Secrets: https://fly.io/docs/apps/secrets/

当時の第一候補は **Railway Free + Volume** だった。SQLiteを継続でき、HTTPSと環境変数を利用できるため。Renderは無料Web ServiceのローカルSQLiteが再起動・再デプロイで消えるので、出席記録には使えないと判断していた。

## デプロイ前チェックリスト

**1〜5はサーバーに入れる人しかできない。** 開発チームはログインできないので，
依頼して結果を受け取る形になる。順番に意味があり，1〜5が済まないと6〜9は試せない。

| # | 内容 | 担当 | 状況 |
|---|---|---|---|
| 1 | DB初期化方法とDBパス環境変数の確定 | 管理者（担当Bが方法を提供） | 済 |
| 2 | DBファイルの保存先を決める（仮想サーバーなのでVolumeのマウントは不要。`DATABASE_URL` が指すパスを決め，バックアップの手順と揃える） | **管理者** | 済。**実際のパスはこの文書に書かない**（下記） |
| 3 | 起動コマンドを `uvicorn app.main:app --host 0.0.0.0 --port <ポート>` 相当にする | **管理者** | 済 |
| 4 | 環境変数を設定する（下記） | **管理者** | 済。`TOKEN_SECRET` は**管理者が生成**し，開発チームは値を知らない |
| 5 | `/health` をヘルスチェックに設定する | **管理者** | 済 |
| 6 | HTTPSでログインCookie・カメラ・QR読み取りを確認する | こちら | ログインは確認済。**カメラとQR読み取りは実機で未確認** |
| 7 | 学内の複数地点・複数時刻で出口IPを確認し，CIDRを決める | こちら | 設定済。複数地点での確認結果は未記録 |
| 8 | 学外回線で出席登録が必ず拒否されることを確認する | こちら | **確認済**（test-report.md のA-3） |
| 9 | `X-Forwarded-For` の実際の並びを確認して `TRUSTED_PROXY_COUNT` を確定する | こちら | **確定済み．**ログは見られなかったが，実地テストの結果から確定できた（「未確定事項」を参照） |

3について：**サーバー上では `0.0.0.0` が必要**（他の端末から繋ぐため）。手元の開発では `127.0.0.1` のままにする。

**依存の入れ方について．** サーバーでは `requirements.txt` ではなく
**`requirements.lock`** を使う。

```
pip install -r requirements.lock
```

`requirements.txt` は直接使う10個しか固定していないため，入れた日によって
starlette などの間接依存が変わる。ロックはCIがテストを通した組み合わせを
そのまま固定したもので，Linux / Python 3.11 向けである（[decisions.md](decisions.md) D-27）。
**版を変えるときは必ずロックを作り直してから入れること**（作り方はロックの先頭に記載）。

4で設定するもの（サーバー上の `.env`，または systemd の `Environment=`）。値はGitへコミットしない。

- `TOKEN_SECRET`: 暗号論的乱数32バイト以上
- `CAMPUS_IP_RANGES`: 実測した大学出口IPのCIDR
- `TRUSTED_PROXY_COUNT`: 実際の信頼プロキシ段数。想定が1台でも実測して決める
- QR・受付時間・レート制限の各設定

## 未確定事項

**`TRUSTED_PROXY_COUNT` は実地テスト（2026-11-12）で確定した．**

当初は「`X-Forwarded-For` の並びをログで確認する」つもりだったが，開発チームは
サーバーのログを見られない。代わりに**実地テストの結果から両側を挟んで確定できた**。

| 設定値が | `get_client_ip` が返すもの | 観察されるはずのこと |
|---|---|---|
| **多すぎる** | `len(parts) < count` なので `""`（[security.py](../app/security.py) 参照） | 学内IPにならないので**学内の全員が拒否される** |
| **少なすぎる** | TCP接続元＝前段プロキシのアドレス（全員同じ値） | **全員が通る**か**全員が落ちる**かのどちらか。学内と学外を区別できない |
| **一致している** | 学生の実IP | 学内は通り，学外は落ちる |

実地テストでは**学内の7人中6人が登録でき，学外（VPN経由）の1人だけが拒否された**。
この2つが同時に成立するのは一番下の行だけなので，設定値は実構成と一致している。

**`X-Forwarded-For` の詐称（A-4）を別途試す必要は無くなった．** 段数が正しければ，
攻撃者が足した値は信頼する範囲の左側に押しやられて読まれない。これは構造から
決まることで，0・1・2の各設定での挙動は `test_security.py` で固定してある。

ただし**段数が変わる構成変更（プロキシの追加や撤去）があればこの値は無効になる**。
そのときは同じ観察（学内から通り，学外から落ちるか）をやり直すこと。

## デモ当日の手当て（同時アクセスで詰まったとき）

全員が同時に出席登録すると，SQLiteの書き込みが1本ずつ順番待ちになる．
既定のロールバックジャーナルは**書き込み中に読み取りも待たせる**ので，
5秒待っても空かないと `database is locked` になり500が返る．

**その場で直せるようにしてある．** `SQLITE_WAL=true` にしてアプリを再起動すれば，
書き手1人と読み手が同時に動けるようになり，待ちが大幅に減る。
**コードの変更もデプロイも要らない**（環境変数だけ）。

```
SQLITE_WAL=true
```

開発チームはサーバーにログインできないので，**当日この作業を管理者に依頼する**
ことになる。事前に伝えておくこと。

| | |
|---|---|
| どの症状のときか | 登録がエラーになる人が出る／教員画面が重い。500が返っていれば濃厚 |
| 既定を false にしている理由 | 実地テストで**素の状態で何人まで耐えるかを測る**ため。先に入れると測れない（[decisions.md](decisions.md) D-25） |
| 元に戻せるか | **環境変数を戻してもファイルはWALのまま。**`PRAGMA journal_mode = DELETE` を手で実行する必要がある |
| バックアップへの影響 | 無い。`VACUUM INTO` はWALでも一貫したスナップショットを取れる |

WALにすると `attendance.db-wal` と `attendance.db-shm` が同じ場所にできる。
`.gitignore` で弾いてあるが，**`-wal` にはまだ本体へ書き戻していない中身が
入っている**ので，バックアップを手でコピーする運用に変える場合は注意する
（`scripts/backup_db.py` を使う限り問題ない）。

## バックアップと復元

### 取り方

```
python -m scripts.backup_db
```

`backups/attendance-日時.db` ができる。**アプリを止める必要はない。**

SQLite は単一ファイルなので `cp` で済みそうに見えるが，**動いている最中にコピーすると書き込み途中の状態を掴んで壊れたコピーになることがある**。スクリプトは `VACUUM INTO` を使い，一貫したスナップショットを取る。

取った直後に自動で検証する。

| 検証 | 何を見るか |
| ---- | ---------- |
| `PRAGMA integrity_check` | ファイルとして壊れていないか |
| 全テーブルの行数の突き合わせ | 中身が元と揃っているか |

どちらかが通らなければ終了コード1で落ちる。**「取れたつもりで開けなかった」を防ぐため**に，取ると検証を1つのコマンドにしてある。

**テストでは示せていないこと。** `tests/test_backup_db.py` は「完全であること」「開けること」は確かめているが，**「動作中にコピーしても壊れないこと」は確かめていない**。テスト中は誰も書き込んでいないので，単純なファイルコピーでも通ってしまう（変異テストで確認済み）。同時書き込みを起こすテストはタイミング依存で不安定になるため書いていない。**保証は `VACUUM INTO` の仕組み側から来ている**。トークン比較の定数時間性を計測で示せないのと同じ状況（test-report.md 参照）。

### いつ取るか

- **実地テストの直前と直後**。実地テストの記録は報告書の素材で，消えたら15人に集まり直してもらうことになる
- 設定を大きく変える前（受付時間，`CAMPUS_IP_RANGES` など）
- アカウントを作り直す前（`seed_data` は `users` が空のときしか動かないので，DBを消す運用になる）

自動化はしていない。サーバーの cron は管理者の領域で，こちらからは触れないため。

### 復元

1. アプリを止める
2. 今のDBを別名で退避する（**上書きしない**。復元したものが期待と違ったとき戻せなくなる）
3. バックアップを `DATABASE_URL` が指す場所にコピーする
4. アプリを起動する
5. ログインして，出席状況の一覧に記録が出ることを確認する

**復元を一度も試していないバックアップは，バックアップではない。**

手順どおりに戻して，実際に使えるところまで通してある（2026-10-19）。使い捨てのDBで，
バックアップ → 別の場所へ復元 → アプリ起動 → 学生のログインと履歴表示 → 教員の
ログインと出席一覧，まで確認した。**ファイルが開けることと，戻した先でアプリが
動くことは別の話**なので分けて確かめている。

### 古いバックアップを戻すときの注意

**確認できているのは「同じスキーマなら戻せる」までである。**

起動時の `create_all` は**無いテーブルは作る**が，**既存テーブルに列は足さない**。

| バックアップを取った後の変更 | 古いバックアップを戻せるか |
| ---------------------------- | -------------------------- |
| テーブルが増えた | 戻せる。起動時に空のテーブルが作られる |
| **既存テーブルに列が増えた** | **戻せない**。起動はするが，その列を使う画面で `no such column` で落ちる |
| CHECK制約が変わった | 戻せるが，**古い制約のまま**になる（SQLiteは後から変更できない） |

実例として，`attendance_window_settings` は 2026-10-14 に増えたテーブルなので，
それ以前のバックアップでも戻せる。一方，`late_until_minutes >= 5` の CHECK制約は
2026-10-19 に足したので，それ以前に作られたDBを戻すと**制約が無い状態**になる。

**`models.py` の既存テーブルに列を足したら，それ以前のバックアップは使えなくなる。**
列を足す変更をするときは，その時点で新しくバックアップを取り直すこと。

### 置き場所

**バックアップの中身は本番と同じで，全出席記録とパスワードハッシュが入っている。**

アプリは認可で守っている（学生は他人の記録を読めない，管理者は出席記録に触れない）が，**ファイルをコピーした時点でその守りは外れる**。ファイルを読める人は全部読める。

部活のサーバーは**管理者3人**が同じアカウントを共有しているので，サーバー上に置けばその3人が読める状態になる。**開発チームの誰でもなく，運用側の3人**である点に注意する。これは受け入れている制約だが，**バックアップを置くことで対象が増える**点は意識しておく。

リポジトリには入れない。`.gitignore` の `*.db` で弾いている。
