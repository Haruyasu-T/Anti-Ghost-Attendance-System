# API設計

[要件定義](requirements.md)・[脅威モデル](threat-model.md)・[DB設計](db-design.md)を前提とする．

方針は，どのエンドポイントでも「誰がアクセスできるか」と「何を検証するか」をサーバー側で必ず判断すること．

## エンドポイント一覧

認可欄の「本人」はログインセッションから取ったユーザー，「担当」は `courses.teacher_id` が一致することを指す．

### 認証

| メソッド | パス           | 認可       | 概要                     |
| -------- | -------------- | ---------- | ------------------------ |
| POST     | `/auth/login`  | 誰でも     | ログイン．レート制限あり |
| POST     | `/auth/logout` | 要ログイン | ログアウト               |
| GET      | `/auth/me`     | 要ログイン | 自分のロールと表示名     |

| POST     | `/courses/{course_id}/attendance-sessions` | teacher＋担当 | 出席セッションを開始                   |

| POST     | `/attendances`    | student    | 出席登録           |
| GET      | `/me/attendances` | 要ログイン | 自分の出席履歴     |

## 認可で特に気をつけること

### `/attendance-sessions/{id}/token` は必ず教員限定にする

このエンドポイントは現在有効なトークンを返す．学生が呼べてしまうと，教室のQRを見ずにトークンが手に入る．そうなると動的QRという対策が丸ごと意味を失い，学外からでも取得できるのでIP検証以外の防御が全部崩れる．

このプロジェクトで一番認可を間違えてはいけない場所なので，実装時とレビュー時に重点的に確認する．

### 学生の記録を読むAPIにIDを受け取らせない

学生の履歴取得は `GET /me/attendances` だけにして，パスにもクエリにもボディにも学生IDを受け取らない．返す対象はログインセッションから取った本人のIDで決める．

`GET /students/{student_id}/attendances` のような形にすると，`student_id` を書き換えて他人の記録を覗く攻撃の入口になる．そういうエンドポイントを作らなければ攻撃は成立しない．

教員が他の学生の記録を見るのは `GET /attendance-sessions/{id}/attendances` 経由だけで，このときも「そのセッションの授業を担当しているか」をサーバー側で確認する．

### 教員のAPIは必ず担当授業かを確認する

ロールが teacher であることだけ確認して `course_id` や `session_id` をそのまま信じると，他の教員の授業の記録を閲覧・改ざんできてしまう．すべての教員向けエンドポイントで「対象の授業の `teacher_id` ＝ ログイン中の教員のID」を確認する．

## `POST /attendances`（出席登録）

システムの心臓部なので，検証の順序と各段階で返すものを細かく決めておく．

### リクエスト

```
POST /attendances
Cookie: session=<ログインセッション>; device_id=<端末識別子>
Content-Type: application/json
X-CSRF-Token: <CSRFトークン>

{ "attendance_session_id": 12, "token": "a3f19c02e5b8d417" }
```

クライアントから受け取るのはセッションIDとトークンだけ．学籍番号も時刻もIPアドレスも「学内にいます」という申告も受け取らない．全部サーバー側で判断する．

### 検証の順序

| #   | 検証                                                   | 失敗時                               |
| --- | ------------------------------------------------------ | ------------------------------------ |
| 1   | ログイン済みか                                         | 401                                  |
| 2   | ロールが `student` か                                  | 403                                  |
| 3   | CSRFトークンが正しいか                                 | 403                                  |
| 4   | アクセス元IPが学内レンジか                             | 403                                  |
| 5   | セッションが存在し `open` か                           | 404 / 409                            |
| 6   | その授業を履修しているか                               | 403                                  |
| 7   | トークンが有効か（現在世代または直前1世代）            | 403                                  |
| 8   | 何回目の読み取りか．`required_scan_count` を超えないか | 409                                  |
| 9   | （1回目のみ）受付時間帯の判定                          | 403                                  |
| 10  | 端末の紐付けを確認                                     | ブロックしない．検知して記録するだけ |
| 11  | トランザクション内で記録．一意制約違反は409に変換      | 409                                  |
| 12  | 監査ログに記録（成功も失敗も）                         | —                                    |

**IP検証をトークン検証より前に置いているのは意図的**．学外からの試行に対して，トークンが有効かどうかの情報を一切返さないため．トークン検証を先にすると，攻撃者は学外から「このトークンはまだ有効か」を試せてしまう．転送したQRの有効性を確認する手段を与えることになる．IP検証を先に置けば，学外からの試行はすべて同じ応答になって何も分からない．

**受付時間帯の判定を2回目以降に適用しないのも意図的**．2回目以降は在室確認で，授業開始から20分以上経った時点で行われるのが普通だから．1回目（`scan_seq = 1`）のときだけ判定する．

この結果，1回目を読まずに再表示の回だけ読もうとした学生は `scan_seq = 1` として扱われ，受付時間帯を過ぎているので拒否される．意図した挙動．

### 成功時のレスポンス

```json
{ "status": "present", "scan_seq": 1, "recorded_at": "2026-07-26T01:32:11Z" }
```

### エラーメッセージをどこまで具体的にするか

学生が自分で対処できる情報は返したいが，攻撃者に手掛かりを与えたくない．この2つがぶつかるので，こう整理した．

| 失敗の種類       | 返すメッセージ                                           | 理由                                                                           |
| ---------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------ |
| IP検証の失敗     | 「学内ネットワークからアクセスしてください」             | 学生が自力で対処できる．学内IPレンジは隠しても意味がない（学内にいれば分かる） |
| トークン期限切れ | 「QRの有効期限が切れました．もう一度読み取ってください」 | 再読み取りを促す必要がある                                                     |
| 受付時間帯外     | 「受付時間を過ぎています」                               | 具体的に返す                                                                   |
| トークンが不正   | 「無効なQRです」                                         | 期限切れと区別しない．改ざんの試行に手掛かりを与えない                         |
| 未履修           | 「この授業の履修者ではありません」                       | 具体的に返す                                                                   |

「期限切れ」と「不正」を区別している点は議論の余地がある．期限切れを区別するのは可用性のため（再読み取りすれば解決すると学生に分かる）だが，攻撃者にも「形式は正しいトークンだった」と伝わる．転送攻撃の文脈では既にQRを持っているので追加情報にならないと判断した．

## その他のエンドポイント

### POST /auth/login

```
{ "login_id": "S0001", "password": "..." }
```

成功したらサーバー側セッション（`login_sessions`）を作り，そのIDをCookieで返す．`HttpOnly` / `Secure` / `SameSite=Lax`．Cookieに入れるのはセッションIDの乱数だけで，ユーザーIDやロールは入れない．ログイン成功時にセッションIDを再発行する（セッション固定攻撃の対策）．

失敗時は401．「IDが存在しない」と「パスワードが違う」を区別しない（アカウントの存在を推測させないため）．

レート制限として，同一IPと同一 `login_id` それぞれについて直近N分間の失敗回数を数え，閾値を超えたら一定時間拒否する（`audit_logs` を検索して判定）．

成功も失敗も `audit_logs` に記録する．パスワードは記録しない．

**`SameSite=Strict` にしない理由**：QRを読み取るとカメラアプリから `/scan` へ遷移する．これは外部コンテキストからのトップレベルGETナビゲーションになるので，Strictだとログイン Cookie が送られず，読み取るたびにログイン画面に飛ばされる可能性がある．そこでLaxにして，状態を変えるPOSTにはCSRFトークンを併用する．

### POST /courses/{course_id}/attendance-sessions

```
{ "scheduled_start_at": "2026-07-27T01:00:00Z" }
```

`scheduled_start_at` は授業の開始予定時刻で，出席／遅刻の判定基準になる．教員が入力する値なので，極端に過去や未来の値は弾く（現在時刻の前後数時間以内くらい）．

同じ授業で `open` のセッションが既にあれば409．

### GET /attendance-sessions/{id}/token

```json
{ "token": "a3f19c02e5b8d417", "rotate_seconds": 5, "next_rotate_at": "2026-07-26T01:32:15Z" }
```

QR表示画面が `rotate_seconds` ごとにポーリングして再描画する．教員のみ・担当授業のみ（前述の通り最重要の認可）．

### POST /attendance-sessions/{id}/rescan

`required_scan_count` を1つ増やす．事前設定ではなく教員がその場で押す．`audit_logs` に `rescan_start` として記録．

### POST /attendance-sessions/{id}/rotate-token

`token_salt` を作り直す．これで出回っている全QRが即座に無効になる．QRが撮影されて拡散された疑いがあるときの緊急対応用．

副作用として，実行した瞬間に読み取り中だった学生も失敗するので，画面上で確認してから実行させる．`audit_logs` に `token_rotate` として記録．

### GET /attendance-sessions/{id}/attendances

履修者全員を返す．出席登録がない学生も「未登録」として含める．履修者名簿との差分を取るのはサーバー側の仕事．

### PATCH /attendances/{id}/

```
{ "status": "present", "reason": "QRの読み取り不良を申告．口頭で在室を確認" }
```

教員・担当授業のみ．`reason` は必須で，空文字やスペースだけなら400で拒否する．

`attendances` を更新して `record_source` を `manual` にする．同じトランザクションの中で `manual_corrections` に監査行を作り，監査ログの書き込みが失敗したら修正自体をロールバックする．記録の残らない修正を作らないため．

記録が存在しない学生への新規追加も同じエンドポイントで扱う（`before_status` がNULLになる）．

`reason` を必須にしたのは，手動修正が出席記録を書き換えられる特権操作だから．記録が残ることを操作者に意識させること自体が抑止になる．入力の手間より監査性を優先した．

### GET /attendance-sessions/{id}/alerts

2種類のアラートを返す．

| 種類           | 判定方法                                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------------------------ |
| 端末の使い回し | `device_bindings` に別アカウントで登録済みの `device_id` からの読み取り（`audit_logs` の `device_conflict`） |
| バースト登録   | 同一 `client_ip` から一定時間内に閾値を超える件数の登録（`attendance_scans` を集計）                         |

どちらもブロックはせず，教員に見せて判断を委ねる．

## 全体に共通すること

### 認可チェックの書き方

各エンドポイントで個別に `if` を書くと，1箇所の書き忘れがそのまま脆弱性になる（脅威モデルにも限界として書いた）．FastAPIの依存性注入（`Depends`）で共通化する．

```
require_login()               … ログイン必須
require_role("teacher")       … ロール確認
require_course_owner(course)  … 担当授業か確認
require_session_owner(sess)   … セッションの授業の担当か確認
```

エンドポイントの実装本体に認可のロジックを書かず，依存関数として宣言的に付ける．レビューのときに「宣言が付いているか」を見るだけで漏れが分かる状態にしたい．

### HTTPステータスの使い分け

| コード | 用途                                                 |
| ------ | ---------------------------------------------------- |
| 400    | リクエストの形式が不正                               |
| 401    | 未ログイン                                           |
| 403    | ログイン済みだが権限がない／検証に失敗した           |
| 404    | 対象が存在しない（他人のリソースを隠す目的でも使う） |
| 409    | 状態の衝突（二重登録・終了済みセッションなど）       |
| 429    | レート制限                                           |

他の教員の授業を指定された場合は403ではなく404を返す．403だと「そのIDのリソースは存在する」ことが分かってしまうため．

### 前提

- 検証に失敗したら常に拒否する．「判定できなかったので通す」という分岐を作らない
- リクエストで送られてきたユーザーID・時刻・IPは認可や判定の根拠にしない
- 通信はHTTPS前提．トークンとCookieを平文で流さない
