# API設計

[要件定義](requirements.md)・[脅威モデル](threat-model.md)・[DB設計](db-design.md)を前提とする．

設計方針は「**どのエンドポイントでも，誰がアクセスできるか（認可）と何を検証するか（バリデーション）をサーバー側で必ず判断する**」こと（②最小権限／④クライアントを信用しない）．

---

## エンドポイント一覧

凡例：認可欄の「本人」はログインセッションから取得したユーザー，「担当」は`courses.teacher_id`が一致することを指す．

### 認証

| メソッド | パス | 認可 | 概要 |
|---|---|---|---|
| POST | `/auth/login` | 誰でも | ログイン．レート制限あり |
| POST | `/auth/logout` | 要ログイン | ログアウト |
| GET | `/auth/me` | 要ログイン | 自分のロールと表示名を返す |

### 教員向け

| メソッド | パス | 認可 | 概要 |
|---|---|---|---|
| GET | `/courses` | teacher | 自分が担当する授業の一覧 |
| POST | `/courses/{course_id}/attendance-sessions` | teacher＋担当 | 出席セッションを開始 |
| GET | `/attendance-sessions/{id}` | teacher＋担当 | セッションの状態 |
| GET | `/attendance-sessions/{id}/token` | **teacher＋担当** | 現在有効なトークンを取得（QR描画用） |
| POST | `/attendance-sessions/{id}/rescan` | teacher＋担当 | 2回目以降のQR再表示を開始 |
| POST | `/attendance-sessions/{id}/close` | teacher＋担当 | セッションを終了 |
| GET | `/attendance-sessions/{id}/attendances` | teacher＋担当 | 出席状況の一覧（履修者全員・未読み込み者を含む） |
| PATCH | `/attendances/{id}` | teacher＋担当 | 出席記録の手動修正 |
| GET | `/attendance-sessions/{id}/alerts` | teacher＋担当 | 異常検知アラートの一覧 |

### 学生向け

| メソッド | パス | 認可 | 概要 |
|---|---|---|---|
| GET | `/scan` | student | QRから遷移する画面（クエリでセッションIDとトークンを受け取る） |
| POST | `/attendances` | student | 出席登録 |
| GET | `/me/attendances` | 要ログイン | **自分の**出席履歴 |

## 重要な認可上の判断

### `GET /attendance-sessions/{id}/token` は絶対に教員限定にする
このエンドポイントは「現在有効なトークン」を返す．**学生が呼べてしまうと，教室のQRを見ずにトークンを取得できてしまい，動的QRという対策そのものが無意味になる**．学外からでも取得できることになり，IP検証以外の防御が全て崩れる．

このプロジェクトで最も認可を間違えてはいけないエンドポイントであり，実装時とレビュー時に重点的に確認する．

### 学生の記録を読むエンドポイントにIDを受け取らせない
学生の履歴取得は`GET /me/attendances`のみとし，**パスにもクエリにもボディにも学生IDを一切受け取らない**．返す対象はログインセッションから取得した本人のIDで決定する．

`GET /students/{student_id}/attendances`のような形にすると，`student_id`を書き換えて他人の記録を覗く攻撃（脅威モデルの「他人の記録への不正アクセス」）の入口になる．**そのような形のエンドポイントを作らないことで，攻撃を構造的に成立させない**．

教員が他の学生の記録を見るのは`GET /attendance-sessions/{id}/attendances`経由のみで，このときも「そのセッションの授業を担当しているか」をサーバー側で必ず確認する．

### 教員のエンドポイントは必ず担当授業かを確認する
ロールが`teacher`であることだけを確認して`course_id`や`session_id`をそのまま信じると，**他の教員の授業の記録を閲覧・改ざんできてしまう**（水平権限昇格）．すべての教員向けエンドポイントで「対象の授業の`teacher_id`＝ログイン中の教員のID」を確認する．

## `POST /attendances`（出席登録）の検証順序

このAPIがシステムの心臓部なので，検証の順序と各段階で返すものを明確に決める．

**リクエスト**
```
POST /attendances
Cookie: session=<ログインセッション>; device_id=<端末識別子>
Content-Type: application/json
X-CSRF-Token: <CSRFトークン>

{ "attendance_session_id": 12, "token": "a3f19c02e5b8d417" }
```

クライアントから受け取るのはセッションIDとトークンのみ．**学籍番号・時刻・IPアドレス・「学内にいます」という申告は一切受け取らない**．すべてサーバー側で判断する．

**検証順序**

| # | 検証 | 失敗時 | 理由・補足 |
|---|---|---|---|
| 1 | ログイン済みか | 401 | |
| 2 | ロールが`student`か | 403 | 教員は出席登録できない |
| 3 | CSRFトークンが正しいか | 403 | Cookie認証のため必要 |
| 4 | **アクセス元IPが学内レンジか** | 403 | 後述の理由により早い段階で判定する |
| 5 | セッションが存在し`open`か | 404 / 409 | |
| 6 | その授業を履修しているか | 403 | |
| 7 | トークンが有効か（現在世代または直前1世代） | 403 | 比較は定数時間で行う |
| 8 | 何回目の読み取りか判定．`required_scan_count`を超えないか | 409 | 同じ回の二重登録を拒否 |
| 9 | （1回目のみ）受付時間帯の判定 | 403 | 出席／遅刻／受付終了をサーバー時刻で決定 |
| 10 | 端末の紐付けを確認 | — | **ブロックしない．検知して記録するのみ** |
| 11 | トランザクション内で記録．一意制約違反は409 | 409 | DBが最終防壁 |
| 12 | 監査ログに記録（成功・失敗いずれも） | — | |

**なぜIP検証を4番目（トークン検証より前）に置くか**

学外からの試行に対して，**トークンが有効かどうかの情報を一切返さないため**である．トークン検証を先に置くと，攻撃者は学外から「このトークンはまだ有効か」を試せてしまい，転送したQRの有効性を確認する手段（オラクル）を与えることになる．IP検証を先に置けば，学外からの試行はすべて同じ応答になり，何も学習できない．

**なぜ受付時間帯の判定を2回目以降に適用しないか**

2回目以降の読み取りは在室確認であり，授業開始から20分以上経過した時点で行われるのが普通だからである．1回目（`scan_seq = 1`）のときだけ受付時間帯を判定する．

この結果として，1回目を読まずに再表示の回だけ読もうとした学生は`scan_seq = 1`として扱われ，受付時間帯を過ぎているため拒否される．意図した挙動である．

**成功時のレスポンス**
```json
{ "status": "present", "scan_seq": 1, "recorded_at": "2026-07-26T01:32:11Z" }
```

**エラーメッセージの粒度について**

学生が自分で対処できる情報は返す必要がある一方，攻撃者に手掛かりを与えたくないという緊張関係がある．今回は次のように整理した．

| 失敗の種類 | 返すメッセージ | 判断 |
|---|---|---|
| IP検証の失敗 | 「学内ネットワークからアクセスしてください」 | 具体的に返す．学生が自力で対処できる情報であり，学内IPレンジは隠しても意味がない（学内にいれば分かる） |
| トークン期限切れ | 「QRの有効期限が切れました．もう一度読み取ってください」 | 具体的に返す．再読み取りを促す必要がある |
| 受付時間帯外 | 「受付時間を過ぎています」 | 具体的に返す |
| トークンが不正（改ざん・別セッション） | 「無効なQRです」 | 期限切れと区別しない．改ざんの試行に手掛かりを与えないため |
| 未履修 | 「この授業の履修者ではありません」 | 具体的に返す |

「トークン期限切れ」と「トークン不正」を区別している点は議論の余地がある．期限切れを区別して返すのは可用性のため（学生が再読み取りすれば解決すると分かる）だが，攻撃者にも「形式は正しいトークンだった」と伝わる．転送攻撃の文脈では既にQRを持っているため追加情報にならないと判断した．

## その他のエンドポイントの仕様

### POST /auth/login

```
POST /auth/login
{ "login_id": "S0001", "password": "..." }
```

- 成功時：ログインセッションのCookieを発行．`HttpOnly` / `Secure` / `SameSite=Lax`
- 失敗時：401．**「IDが存在しない」と「パスワードが違う」を区別しない**（アカウントの存在を推測させないため）
- レート制限：同一IPおよび同一`login_id`について，直近N分間の失敗回数が閾値を超えたら一定時間拒否する（`audit_logs`を検索して判定）
- 成功・失敗のいずれも`audit_logs`に記録する．**パスワードは記録しない**

**なぜ`SameSite=Strict`ではなく`Lax`か**

QRを読み取るとカメラアプリから`/scan`へ遷移する．この遷移は外部コンテキストからのトップレベルGETナビゲーションになるため，`Strict`ではログインCookieが送られず，読み取るたびにログイン画面に飛ばされる可能性がある．そこで`Lax`とし，状態を変更するPOSTにはCSRFトークンを併用してCSRF対策を担保する．

### POST /courses/{course_id}/attendance-sessions

```
{ "scheduled_start_at": "2026-07-27T01:00:00Z" }
```

- `scheduled_start_at`は**授業の開始予定時刻**．出席／遅刻の判定基準になる
- 教員が入力する値なので，過度に過去・未来の値を弾くバリデーションを入れる（例：現在時刻の前後数時間以内）
- 同一授業で`open`のセッションが既にある場合は409

### GET /attendance-sessions/{id}/token

```json
{ "token": "a3f19c02e5b8d417", "rotate_seconds": 5, "next_rotate_at": "2026-07-26T01:32:15Z" }
```

- QR表示画面が`rotate_seconds`ごとにポーリングして再描画する
- 教員のみ・担当授業のみ（前述の通り最重要の認可）

### POST /attendance-sessions/{id}/rescan

- `required_scan_count`を1つ増やす
- 事前設定ではなく，教員がその場で押す（要件の決定事項通り）
- `audit_logs`に`rescan_start`として記録

### GET /attendance-sessions/{id}/attendances

履修者全員を返す．出席登録がない学生も「未登録」として含める（履修者名簿との差分を取るのはサーバー側の責務）．

```json
{
  "session": { "id": 12, "course_name": "情報セキュリティ", "required_scan_count": 2 },
  "rows": [
    { "login_id": "S0001", "display_name": "…", "status": "present",
      "scan_count": 2, "record_source": "auto", "alerts": [] },
    { "login_id": "S0002", "display_name": "…", "status": "present",
      "scan_count": 1, "record_source": "auto", "alerts": ["1回目のみ"] },
    { "login_id": "S0003", "display_name": "…", "status": "late",
      "scan_count": 1, "record_source": "manual", "alerts": [] },
    { "login_id": "S0004", "display_name": "…", "status": null,
      "scan_count": 0, "record_source": null, "alerts": [] }
  ]
}
```

### PATCH /attendances/{id}

```
{ "status": "present", "reason": "QRの読み取り不良を申告．口頭で在室を確認" }
```

- 教員・担当授業のみ
- `attendances`を更新して`record_source`を`manual`にする
- **同一トランザクション内で`manual_corrections`に監査行を作る**．監査ログの書き込みが失敗したら修正自体をロールバックする（記録のない修正を残さない）
- 記録が存在しない学生に対する新規追加も同じエンドポイントで扱う（`before_status`がNULLになる）

### GET /attendance-sessions/{id}/alerts

2種類のアラートを返す．

| 種類 | 判定方法 |
|---|---|
| 端末の使い回し | `device_bindings`に別アカウントで登録済みの`device_id`からの読み取りを検知（`audit_logs`の`device_conflict`） |
| バースト登録 | 同一`client_ip`から一定時間内に閾値を超える件数の登録があった（`attendance_scans`を集計） |

いずれも**ブロックはせず，教員に提示して判断を委ねる**（脅威モデルの決定通り）．

## 共通の設計方針

### 認可チェックの実装方法
各エンドポイントで個別に`if`を書くと**1箇所の書き忘れが脆弱性になる**（脅威モデルに限界として記載済み）．FastAPIの依存性注入（`Depends`）で共通化する．

```
require_login()               … ログイン必須
require_role("teacher")       … ロール確認
require_course_owner(course)  … 担当授業か確認
require_session_owner(sess)   … セッションの授業の担当か確認
```

エンドポイントの実装本体に認可のロジックを書かず，依存関数として宣言的に付ける．レビュー時に「宣言が付いているか」を見るだけで漏れを検出できる状態にする．

### HTTPステータスの使い分け

| コード | 用途 |
|---|---|
| 400 | リクエストの形式が不正 |
| 401 | 未ログイン |
| 403 | ログイン済みだが権限がない／検証に失敗した |
| 404 | 対象が存在しない（他人のリソースを隠す目的でも使う） |
| 409 | 状態の衝突（二重登録・既に終了したセッションなど） |
| 429 | レート制限 |

他の教員の授業を指定された場合は403ではなく**404を返す**方針とする．403だと「そのIDのリソースは存在する」ことが分かってしまうため．

### 全エンドポイント共通の前提
- 検証に失敗した場合は常に拒否する（⑤安全なデフォルト）．「判定できなかったので通す」という分岐を作らない
- リクエストで送られてきたユーザーID・時刻・IPは認可や判定の根拠にしない（④）
- 通信はHTTPS前提（トークンとCookieを平文で流さない）

## フェーズ2で見つかった追加の脅威

設計を詰める過程で，フェーズ1の脅威モデルに無かった論点が3つ出てきた．[脅威モデル](threat-model.md)に追記済み．

1. **トークン発行APIへの不正アクセス** — `GET /attendance-sessions/{id}/token`を学生が呼べると動的QRの意味がなくなる
2. **トークン秘密鍵の漏洩** — 鍵から任意の有効トークンを生成でき，教室にいなくても出席できる
3. **CSRF** — Cookie認証のため，教員が細工されたページを開くと意図しない手動修正を実行させられる可能性がある
