# 画面設計

[要件定義](requirements.md)と[API設計](api-design.md)に対応する画面のラフ．担当Cが`app/templates/`に実装する．

**前提**
- 学生の画面はスマホの縦画面を想定（専用アプリは作らない）
- 教員のQR表示画面は**教室のプロジェクター投影**を想定．離れた席からでもQRが読める大きさにする
- 教員の管理画面はPCのブラウザを想定

---

## 画面一覧と遷移

```
                    ┌──────────────┐
                    │  ログイン    │
                    └──────┬───────┘
                           │ role で分岐
            ┌──────────────┴──────────────┐
            ▼                             ▼
     【教員】授業一覧              【学生】ホーム
            │                             │
            ├─ セッション開始 ──┐         ├─ QRを読み取る ──┐
            │                   ▼         │                  ▼
            │            QR表示画面       │           読み取り結果
            │            （投影用）       │
            │                   │         └─ 出席履歴
            └─ 出席状況一覧 ◀───┘
                    │
                    └─ 手動修正
```

QRを読み取った場合は，カメラアプリから直接 `/scan` に遷移する（ログイン画面を経由することもある）．

```
┌────────────────────────────┐
│                            │
│      出席管理システム      │
│                            │
│  学籍番号 / 職員番号       │
│  ┌──────────────────────┐  │
│  │                      │  │
│  └──────────────────────┘  │
│                            │
│  パスワード                │
│  ┌──────────────────────┐  │
│  │                      │  │
│  └──────────────────────┘  │
│                            │
│  ┌──────────────────────┐  │
│  │       ログイン       │  │
│  └──────────────────────┘  │
│                            │
│  ⚠ IDまたはパスワードが   │
│    正しくありません        │
│                            │
└────────────────────────────┘
```

- エラーメッセージは「IDが存在しない」と「パスワードが違う」を**区別しない**（アカウントの存在を推測させない）
- レート制限にかかった場合のみ「しばらく待ってから再度お試しください」と表示する
- ログイン成功後は`role`に応じて教員画面／学生画面へ振り分ける

**授業前にログインを済ませてもらう案内をここに置く**：QRを読んでから未ログインだと，ログインしている間にトークンの有効期限（5秒）が切れて読み直しになる．「授業開始前にログインしておいてください」という一文を表示する．

## S3. 【学生】読み取り結果

QRから`/scan?s=12&t=a3f19c...`に遷移し，`POST /attendances`の結果を表示する．

**成功（出席）**
```
┌────────────────────────────┐
│                            │
│           ✓                │
│                            │
│      出席を記録しました    │
│                            │
│   情報セキュリティ         │
│   2026/07/27 10:02         │
│   区分：出席               │
│                            │
│  ┌──────────────────────┐  │
│  │       ホームへ       │  │
│  └──────────────────────┘  │
└────────────────────────────┘
```

**成功（遅刻）**
```
│           ✓                │
│      出席を記録しました    │
│   区分：遅刻               │
│   （開始から8分後の登録）  │
```

**成功（2回目以降＝在室確認）**
```
│           ✓                │
│    2回目の確認が完了       │
│    しました                │
│   区分：出席（変更なし）   │
```

**失敗**

| 状況 | 表示 | 次の行動を示す |
|---|---|---|
| 学外からのアクセス | 「学内ネットワークに接続してください」 | Wi-Fi設定を確認する |
| トークン期限切れ | 「QRの有効期限が切れました」＋**再読み取りボタン** | もう一度読む |
| 無効なQR | 「無効なQRです」 | 教員に申し出る |
| 受付時間外 | 「受付時間を過ぎています」 | 教員に申し出る |
| 未履修 | 「この授業の履修者ではありません」 | — |
| 既に登録済み | 「この回の出席は既に登録されています」 | — |

```
┌────────────────────────────┐
│           ✕                │
│  QRの有効期限が切れました  │
│                            │
│  QRは5秒ごとに更新されます．│
│  もう一度読み取ってください．│
│                            │
│  ┌──────────────────────┐  │
│  │   📷 もう一度読む    │  │
│  └──────────────────────┘  │
└────────────────────────────┘
```

**期限切れの再読み取りは1タップで戻れるようにする**．5秒更新なので失敗はある程度発生する前提で，やり直しの摩擦を最小にしておく．ここが煩雑だと手動修正への依存が増え，[脅威モデル](threat-model.md)に書いた「可用性を削るとセキュリティも落ちる」状態になる．

## S6. 【教員】QR表示（投影用）

```
┌──────────────────────────────────────────────┐
│  情報セキュリティ  第10回                    │
│                                              │
│        ┌────────────────────────┐            │
│        │                        │            │
│        │                        │            │
│        │       ▓▓  ▓▓▓ ▓▓      │            │
│        │       ▓ ▓▓ ▓  ▓ ▓     │            │
│        │       ▓▓▓  ▓▓▓▓▓      │            │
│        │        （QRコード）    │            │
│        │                        │            │
│        │                        │            │
│        └────────────────────────┘            │
│                                              │
│         次の更新まで  ● ● ● ○ ○             │
│                                              │
│  受付中：出席（10:05まで）                   │
│  登録済み：32 / 40 名                        │
│                                              │
│  [2回目のQRを表示]        [セッション終了]   │
└──────────────────────────────────────────────┘
```

**設計上のポイント**
- QRは画面の大部分を占める大きさにする（教室後方からスマホで読める必要がある）
- **更新までの残り時間を視覚的に出す**（●○のインジケータやプログレスバー）．切り替わる直前に読み始めて失敗するのを減らすため
- 受付中の区分（出席／遅刻）と締切時刻を表示し，教員が状況を把握できるようにする
- 登録済み人数をリアルタイムに更新する
- 5秒ごとに`GET /attendance-sessions/{id}/token`をポーリングして再描画する

**「2回目のQRを表示」ボタン**
- 押すと`POST /attendance-sessions/{id}/rescan`を呼び，`required_scan_count`が増える
- 事前設定ではなく**教員がその場で押す**方式（要件の決定事項通り．タイミングを予測されると効果が落ちる）
- 押した後は表示が「3回目のQRを表示」に変わる（回数の上限は設けない）
- 押す前に確認ダイアログは出さない（学生に気付かれる前に素早く実行できるようにする）

```
└──────────┴────────┴──────┴──────┴────────┴───────────────┘
```

**設計上のポイント**
- **履修者全員を表示する**．未登録者が「行がない」のではなく「区分が空欄」として並ぶ（欠席者を見落とさないため）
- 「1回目のみ」の学生に警告マークを出す．ただし**自動で欠席にはしない**（機器トラブルと中抜けを区別できないため，判断は教員に委ねる）
- アラートは画面上部にまとめて出し，該当行にもマークを付ける
- 手動修正済みの記録は「手動✎」と表示して自動判定と区別する

**手動修正のダイアログ**
```
┌────────────────────────────────────┐
│  出席記録の修正                    │
│                                    │
│  対象：24…0004 ○○                │
│  現在：記録なし                    │
│                                    │
│  変更後                            │
│  ( ) 出席   ( ) 遅刻   ( ) 欠席    │
│                                    │
│  理由（監査ログに記録されます）    │
│  ┌──────────────────────────────┐  │
│  │                              │  │
│  └──────────────────────────────┘  │
│                                    │
│  ⚠ この操作は「誰が・いつ・何を   │
│    どう変更したか」が記録されます  │
│                                    │
│         [キャンセル]  [修正する]   │
└────────────────────────────────────┘
```

- **理由の入力欄を必ず置き，記録される旨を画面に明示する**．手動修正は特権操作であり，記録が残ることを操作者に見せること自体が不正の抑止になる（⑥追跡可能性）
- 理由は任意入力とするか必須とするかは実装時に決める（必須にすると救済が遅れる場面がありうる）

## 画面から見たセキュリティ上の注意（担当Cへの申し送り）

フロント実装で踏みやすい落とし穴を挙げておく．レビュー時にここを確認する．

1. **トークンを`localStorage`に保存しない**．QRから受け取ったトークンはその場で送信するだけで，保持する必要がない．保存するとXSSで盗まれる経路を作る
2. **`device_id`をJavaScriptから触らない**．HttpOnlyのCookieなのでそもそも読めないが，別途JSで独自の端末IDを作って送る実装にしてはいけない（クライアント側で偽装できるものを判定に使うことになる）
3. **時刻をクライアントで計算して送らない**．「開始から何分後か」の判定はサーバーが行う．画面に出す残り時間の表示は表示専用と割り切る
4. **画面の出し分けで権限を制御した気にならない**．「学生には修正ボタンを表示しない」はUIの都合であって認可ではない．APIを直接叩かれる前提で，サーバー側の認可が本体
5. **エラーメッセージをそのまま画面に出す前に確認する**．サーバーの例外メッセージやスタックトレースを表示すると内部構造が漏れる
6. **QRの描画はクライアント側で行う**（`qrcode.js`等）．サーバーから画像を返す必要はなく，トークン文字列だけを受け取って描画すればよい

## フェーズ3での実装順序（担当C）
1. ログイン画面（S1）… 他の画面の前提になる
2. 学生の読み取り結果画面（S3）… 担当A・Bのコア実装の動作確認に使える
3. 教員のQR表示画面（S6）… ポーリングと再描画
4. 教員の出席状況一覧（S7）… 一覧と手動修正
5. 学生ホーム・履歴（S2・S4）
