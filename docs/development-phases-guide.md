各フェーズで「何をやるか」「何が成果物か」「どの設計原則を意識するか」をまとめた実施手引きです．
開発中はこのファイルを参照しながら進めます．

> セキュリティ・バイ・デザインの原則
> ①脅威を設計段階から織り込む ②最小権限 ③多層防御 ④クライアントを信用しない ⑤安全なデフォルト ⑥追跡可能性

### 成果物

## フェーズ1：要件と脅威モデル（目安 3〜4日 / ★必ず2人で）

**このプロジェクトで最も差別化になる工程．コードより先にやる．**

### やること
1. **機能要件を洗い出す**：
   - 教員：出席セッションを開始／QRを表示／出席状況を確認．
   - 学生：QRを読み込む／自分の出席登録．
2. **脅威モデルを作る**：「誰が」「どうやって」不正できるかを書き出す．
3. 各脅威に対して **対策** と **対応する設計原則** を紐づけ，**残る限界** まで正直に書く．

### 脅威モデル表（この形で docs/threat-model.md に）
| 脅威 | 攻撃の内容 | 対策 | 設計原則 | 残る限界 |
|---|---|---|---|---|
| QR転送 | スクショを欠席者に送る | 動的QR（短命トークン） | 多層防御 | 更新間隔内の転送は理論上可 |
| Wi-Fi偽装 | 学外から学内を装う | サーバー側IP検証 | クライアントを信用しない | VPN経由の学内IP取得は突破余地 |
| 二重出席 | 何度も登録する | 一意制約でブロック | 安全なデフォルト | — |
| 権限の逸脱 | 学生が他人の記録を操作 | ロールベースの権限分離 | 最小権限 | — |

### 成果物
- `docs/requirements.md`（機能要件），`docs/threat-model.md`（脅威モデル表）．

### 意識する原則
- ①脅威を設計段階から織り込む，を体現する工程．**表の中身は必ず自分たちの言葉で議論して埋める**（AIに丸投げしない）．

## フェーズ2：設計（目安 3〜4日 / 2人で）

### やること
1. **DB設計**：テーブルを決める．最低限この4つ．
   - `users`（学生・教員．roleを持たせて権限分離）
   - `courses`（授業）
   - `sessions`（出席セッション．開始時刻・有効なトークン・状態）
   - `attendances`（出席記録．誰が・いつ・どのIPから．一意制約）
2. **API設計**：エンドポイントを紙／Markdownに書き出す．例：
   - `POST /sessions`（教員：セッション開始）
   - `GET /sessions/{id}/token`（現在有効なトークンを取得）
   - `POST /attendances`（学生：出席登録．ここでトークン検証＋IP検証）
   - `GET /sessions/{id}/attendances`（教員：出席状況）
3. **画面設計**：教員画面（QR表示），学生画面（読み込み結果）のラフ．
4. **どこで何を検証するか**を設計に明記：トークン期限・IPレンジ・重複，すべて **サーバー側** で．

### 成果物
- `docs/db-design.md`，`docs/api-design.md`，画面ラフ．

### 意識する原則
- ②最小権限（roleで操作を分ける），④クライアントを信用しない（検証は全部サーバー），⑤安全なデフォルト（検証失敗＝拒否）を設計に落とす．

## フェーズ3：コア実装（目安 1〜1.5週間 / 分担）

**セキュリティの心臓部から作る．UIは最後．**

### 実装順序
1. **動的トークンの生成・検証**（`security.py`）
   - 有効期限つきの短命トークンを発行．検証時に「期限切れ／不正」は拒否．
   - 秘密鍵やシークレットはコードに直書きせず環境変数に（追跡可能性・安全なデフォルト）．
2. **サーバー側でのアクセス元IP判定**（`security.py`）
   - リクエスト元IPが学内レンジかを判定．クライアントの申告は使わない．
   - プロトタイプでは「学内とみなすIPレンジ」を設定ファイルで定義しておく．
3. **出席登録API + 二重登録防止**（`main.py` / `models.py`）
   - トークン検証 → IP検証 → 重複チェック の順に通過した場合のみ記録．
   - DBの一意制約（授業×学生）で二重登録を根本から防ぐ．
4. **ログ記録**（追跡可能性）
   - いつ・誰が・どのIPから・成功/失敗を記録．
5. **UI**（`templates/`）
   - 教員：数十秒ごとに更新されるQRを表示．
   - 学生：読み込み → 結果表示．

### 成果物
- 動作する`app/`一式，環境変数の例（`.env.example`）．

### 意識する原則
- ③多層防御（トークン＝時間，IP＝場所，一意制約＝重複，を積み重ねる），⑥追跡可能性（ログ）．
- **生成したコードは1つずつ「なぜこうなっているか」を確認**してからマージ．

## フェーズ4：結合とテスト（目安 3〜4日 / 2人で）

### やること
1. **正常系テスト**：2人のスマホで実際に読み，出席が記録されるか確認．
2. **攻撃テスト（これ自体が面接ネタ）**：
   - 期限切れのQRを読む → 拒否されるか．
   - QRのスクショを時間差で使う → 更新されて無効か．
   - 二重に登録する → ブロックされるか．
   - （可能なら）学外っぽいIPからのリクエスト → 拒否されるか．
3. 結果を **テスト記録** として残す．「どんな攻撃を試し，どう防げたか」を表に．

### 成果物
- `docs/test-report.md`（攻撃シナリオと結果）．

### 意識する原則
- 設計した対策が実際に効くかを検証．**防げなかったケースも正直に記録**する（限界の把握）．
